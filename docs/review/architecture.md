## (a) Summary verdict

**Conditionally sound, two deliberate bets not yet paid off.** The host half is a careful,
well-evidenced mirror of the official mcp-client machinery (reconnect budget, generation-swap
discipline, naming contract verified byte-for-byte against the installed rc.1 artifact), and
the per-agent-scope injection gate is the *architecturally right* mechanism for the locked R3
"model-visible set, not exec denial" requirement: registration through each live agent's scope
ctx is the only way to make the gate airtight with no global-layer transient window, and the
integration suite proves the registry-level claim with a real ToolRuntime + real dsh-scope
contexts (`tests/host/agents.spec.ts`, mount recipe in `docs/host-notes.md §b`). What keeps this
from a clean pass: (1) two **undeclared runtime imports** (`@deepseek-ai/dsh-timeout`,
`zod`) that load only by fallback-farm/hoisting luck — the official peer model declares
dsh-timeout (`@deepseek-ai/dsh-mcp-client` package.json peers); (2) **workspace membership is
frozen at agent adoption** with no reaction to workspace create/delete, so live sessions can
permanently drift out of (or into) the documented "sessions outside any workspace get no MCP
tools" contract; (3) the applier adopts **every** published agent — including in-process
delegation children, which receive MCP tools in their *own* scope layer, where the platform's
`restrict()` semantics (filters apply to the inherited surface only, never a scope's own
layer) can no longer narrow them — an unverified interaction with rc.1 subagent `toolFilter`
that the current test harness (plain-ctx emits, no real delegation) cannot catch; and
(4) reconcile re-registers every enabled server × live agent on every settings commit
(force path), a churn/teardown-registration burst that a two-line guard would eliminate.
Package/install shape matches the official third-party model (verified live in M0/M1 and
against `dsh-client-ui-settings-plugins`' manifest); the single-row settings-driven manager is
justified over the official one-row-per-server model by the locked UI-driven requirements.
Deviations from rc.1 official behavior (fast apply instead of connect-gated activation,
credentials-based env/headers, skipped rc.1 image bridge, client identity `0.0.1`, fixed
reconnect defaults) are all documented and defensible individually — but "tool semantics
identical to official mcp-client" (`docs/design.md:78`) is a stronger claim than the shipped
surface, and the doc trail should say so explicitly (see ARCH-6, ARCH-13).

## (c) Validated strengths (checked, not assumed)

1. **Naming contract is byte-identical to the installed official artifact.** `publicToolName` (`tools.ts:79-85`: `mcp__<serverName>__<rawName>`, ≤64 `[A-Za-z0-9_-]`, 12-hex SHA-256 over `serverName\0rawName` on lossy normalization) matches the anchor `dsh-mcp-client/lib/index.js` constants and algorithm exactly (MAX_PUBLIC_NAME_LENGTH 64 / INVALID_NAME_CHARS / HASH_LENGTH 12 / same truncation expression), and matches ref-dsh rc.5 `tools.ts:96-102`.
2. **Reconnect/generation discipline mirrors official rc.1** (verified against anchor `dsh-mcp-client`: defaults 500/30_000/10, `resolveReconnectPolicy` validation identical, stability-window budget reset at `maxDelayMs`, give-up commits empty defs, 5 s generation-close discipline, serialized sync chain, fetch-then-commit with previous generation kept on fetch failure) — `server.ts:205-231,254-287,295-365` vs anchor lib lines 456-589.
3. **The injection gate is the correct mechanism for R3 and it is airtight at the layer level.** rc.1 `ToolRuntime.register` derives visibility and effect ownership from the ctx reached through (`dsh-tools` `register()` → `layers.effect(this.ctx,…)`; `ScopedLayers.effect` "ctx that determines both scope visibility and effect ownership"), so registering only through `agent.ctx.tools.register` (`agents.ts:194`) never touches the global layer — proven by the suite's `ctx.tools.get(name)` → `undefined` assertion (`docs/host-notes.md:101-103`). Registration-into-scope is the right tool versus global-register + `restrict()`: a global registration would be visible to every (including off-workspace) agent until a per-agent restriction lands — a real leak window; per-scope registration has none (see Axis 5).
4. **Settings-domain integration uses the rc.1 API exactly as designed**: `installSection` with a *stored* live thunk (`index.ts:64,81-83` — verified `setSource` receives `() => scope.get()` in the anchor implementation), `onChange` at attach and per committed value change (via `scope.watch`, deep-equal-gated in the provider), and a `validate` hook that refuses writes host-side (`index.ts:87-92`) — the M0 stale-write fence and host-side refusal are evidenced live (`M0.md:47-55`).
5. **Install/package shape is faithful to the official third-party model**: `dsh.bundle.patch` + appended bundle order after `dsh-web-app` (`M0.md:10-18`), dual-face `exports["./client"]` + `dsh.client{inject,platform}` whose inject list equals the official `dsh-client-ui-settings-plugins` list, `files` covering lib/types + patch, tgz contents verified complete, restart-documented first-boot module-scan race (`README.md:34-35`, honest). The chamber-bridge recon confirms the official SettingsRoot auto-surfaces third-party `settings.section` entries without chamber involvement (`docs/recon/chamber-bridge.md:18-19`) — R4's "chamber zero code involvement" claim holds in this deployment.
6. **Disposer/effect discipline is consistently fiber-owned**: all subscriptions are `ctx.effect`-wrapped (`index.ts:54-60,76-78`, `manager.ts:170-181`, `agents.ts:250-266`); cordis tears effects down LIFO (`disposables.splice(0).reverse()` in anchor cordis), so the intended order (manager dispose → applier teardown) holds in both teardown orders thanks to `disposed`/`isAlive` guards (`agents.ts:116,121,232-244`); `agent/disposed` deliberately drops bookkeeping only and never double-disposes scope entries (`agents.ts:255-259`, semantics verified against `ScopedLayers.effect` ownership) — a genuinely subtle hazard handled correctly.
7. **Single-instance guard mirrors the official reservation pattern** (anchor mcp-client reserves `serverName` per scope/root with a WeakMap; this reserves per `ctx.root` with a WeakSet, `index.ts:43-60`) — duplicate activation fails loud instead of shadowing.
8. **Child env hygiene and per-attempt credential resolution follow the official rule** (empty stored value ≡ absent; resolve per attempt, never cached) and match the rc.1 credentials API contract (`dsh-credentials` d.ts: per-call `resolve`, empty-is-absent); M0 marker-file evidence shows real resolution into a spawned child (`M0.md:57-75`).
9. **Workspace membership rule re-implements the official predicate faithfully**: `workspaceIdOf` = canonical-realpath equality against registry paths (`workspace.ts:39-50`), which is exactly dsh-workspace's attach rule (anchor `dsh-workspace`: "if cwd !== this.record.path → cannot attach"; canonical path from `fs.realpath`), so workspace-less/subdir sessions behave like the platform's own membership, and the "no workspace ⇒ no tools" policy (`agents.ts:6-8`, `README.md:78-79`) is consistent with platform semantics (subdir cwd sessions are genuinely workspace-less in dsh).
10. **Client half bundle hygiene**: runtime imports are only `react` + local modules (checked every `src/client/*` import); everything cross-package is type-only or service-injected, so the externals/purity gate cannot silently inline drift — and the controller is framework-free and unit-tested (`tests/client/controller.spec.ts`), keeping the save-plan semantics (whole-array `servers` op, atomic per-workspace path ops, removal cascade for credential refs) reviewable without React.

## (d) Per-axis conclusions

### Axis 1 — Completeness vs locked scope
R1–R4 are implemented with the evidence trail demanded (wire + render tests for the section; live namespace + supervisor on scratch instances; real-registry gate tests; live `dsh plugin add` install). The per-workspace-off mechanism — per-agent-scope registration through `agent.ctx` (`agents.ts`), never global — is **architecturally sound** given how rc.1 derives tool views: `view(scope)`/`schemas(scope)` resolve the agent's own layer plus inherited layers per scope key, so an off-workspace agent structurally cannot see the tools (no global layer, no restriction schedule to race). The "sessions outside any workspace get no MCP tools" choice is documented consistently (`README.md:78-79`, `design.md:73`, module docstring `agents.ts:6-8`) and mirrors the platform's own membership rule — but its *runtime* correctness is undermined by the frozen-at-adopt resolution (ARCH-2) and it was never observed at the real assembly layer (ARCH-4). C1–C6 cuts are respected in code (no policy/pause/CLI/naming/config-file surfaces; "status visualization" stayed within the read-only off-count badge). No over-build found beyond test scaffolding; the only scope-adjacent extras (env-key/header secret rows, removal cascade, off-count badge) are required by the locked settings-UI brief. One genuine doc bug: acceptance's data model contradicts the shipped model (ARCH-8).

### Axis 2 — Package/install model
Matches the official model on every verified axis: manifest shape mirrors `dsh-web-app` (bundle) × `dsh-client-ui-settings-plugins` (client face) hybrids — exports/files/`dsh.client.inject` list are exactly the official vocabulary; `dsh plugin add` appends the bundle after `dsh-web-app` (M0 live: `base, web-app, dsh-mcp-scope`); row insertion semantics of the patch format are as used by every official bundle (`- insert: [{id, name}]`, no group targeting, no config replace hazards); the browser half is discovered via `dsh.client` + `exports["./client"]` and served in the boot graph (M0/M1 evidence); client-side optional-negative-verdict caching explains the documented restart requirement (recon §4c). **Uninstall story** is honest and complete for a dsh whose data model keeps namespaces/credentials after package removal (README documents manual cleanup; reinstall restores prior config — a defensible property, worth stating). **Collision risk**: row id `mcp-scope` sits in the shared flat id space; twin inserts by another bundle are ill-defined in the loader's id-keyed diff (ARCH-12) — low probability, mitigation cheap. **Upgrades**: dsh version upgrades swap the launcher tree and re-heal the fallback farm while `$DSH_HOME` persists (chamber-bridge recon), so the plugin survives and re-resolves peers from the new closure; the real exposure is peer-range drift (`^0.1.2-rc.1` allows any 0.1.x) against an `installSection`/events API that changed between rc's before — monitor on the next dsh bump. Package upgrades are `dsh plugin … update` + restart, with reconcile auto-activating/deactivating on `dsh.bundle` presence changes (recon §2b). The one true gap in this axis is ARCH-1 (undeclared runtime imports) — the model is right, the declared surface is not.

### Axis 3 — Module decomposition & data flow
Entry → namespace → manager → supervisors → applier is cleanly separated with narrow interfaces (`ManagerLogger`, `AgentRegistryLike`, `WorkspaceRegistryLike`, `ServerPushState`), and the only real blur is the *manager owning the applier's enablement source*: `overrides: () => options.getDoc().overrides` (`manager.ts:91`) couples the applier's semantics to the manager's doc read, but the live-thunk design (`getDoc` never cached) keeps it honest — validated by the documented earlier bug (stale overrides snapshot, host-notes (c)6). Ordering assumptions that matter: (a) `createManager` before `installSection` with an EMPTY_DOC source — safe only because apply is synchronous (ARCH-9); (b) agent/created adoption vs. workspace attach — the plugin correctly does not depend on attach events (reads `workspaceRegistry.list()`), but freezes the result (ARCH-2); (c) canonical-cwd resolution at adopt with `realpathSync` — matches platform rule, staleness caveat as (b); (d) `ctx.agents.roots()` adoption scan runs inside the effect after listeners are armed — no double-adopt race (`agents.ts:250-260`, comment + `entries.has` guard); (e) event subscriptions: `agent/created`/`agent/disposed` cannot miss (untagged admission verified) and cannot double-fire (adopt/entries guards) — the double-fire risk lives in the **two reconcile entry points** (attach `onChange` + `scope.watch`) which are idempotent but *not cheap* (ARCH-5); `settings/updated`-family deep-equal gating was verified to fire `onChange` only on resolved-value commits — a revision-only (raw-section) change correctly does not reconcile, and the UI correctly re-reads revision from the forwarded `settings/document-updated` — so "ops that normalize away" (empty override rows, default-equal writes) produce no host action and no semantic drift. SetSource live-thunk usage is correct and better than a `scope.watch` subscription at the entry (one source of truth, one indirection).

### Axis 4 — Cordis effect/disposer discipline
Every registration is effect-wrapped; guards (`disposed`, `isAlive`, WeakSet instance guard with disposer) cover HMR/unload, row reload, and double-dispose of scope entries (bookkeeping-drop on `agent/disposed` is the right call — verified layer ownership). LIFO teardown makes manager-dispose → applier-teardown ordering safe in either interleaving with the agent registry. Double-dispose hazards are mitigated to a warn-and-continue (`revokeApplied` try/catch, `agents.ts:147-154`); the residual window (revoke between scoped-unwind and `agent/disposed` while the registry still answers `get`) is real but narrow and idempotent-tolerant — acceptable, worth a comment. The reload path of the loader row itself (patchReload removing/readding the row) could trip the instance guard during overlapping dispose/apply — theoretical, cordis reload disposes before mounting; noted, not blocking.

### Axis 5 — Design optimality & alternatives
- **Single-row settings-driven manager vs official one-row-per-server**: the official model (loader rows per server with config-replacing patches) cannot satisfy R1/C6 (UI add/remove at runtime, no config-file/CLI surface, no patch reload for every add). The settings-domain doc + one manager row is the right call, at the cost of re-implementing the official supervisor instead of reusing `@deepseek-ai/dsh-mcp-client` (impossible: official registers globally into its own ctx and offers no defs-without-registration hook — the per-workspace gate requires the split, which host-notes (c)2 documents). Acceptable, deliberate debt: the mirror must be re-diffed against official on every dsh bump (see Axis 6).
- **Per-agent registration vs global + per-scope restrict()**: per-agent is *correct* for airtightness (no transient visibility for off-workspace/workspace-less agents); global+restrict cannot be applied atomically with defs arrival (restrict validates against known names) and leaks in the interim. The tradeoff is restrict-immunity of own-layer entries (ARCH-3) — the platform's own exemption semantics — and duplication across agents. On balance per-agent is right for R3; ARCH-3 is the residual to verify/decide.
- **Dict-of-dicts overrides vs array**: dict-of-dicts gives atomic single-path set/unset per (workspace, server) and matches the settings path-op API (`unset ['overrides', ws, s]` removes presence without rewriting siblings) — better than array rewrites under concurrent multi-client writes; the only cost is a stale acceptance.md (ARCH-8).
- **Schema forward-compat**: schemastery defaults + composition base + `replace({})` semantics give a clean reset story; new fields added later default in without touching stored docs. The `validate` hook covers cross-field constraints the schema cannot express (duplicates). One caution: `validate` throwing a *plain Error* (not a typed settings error) makes client classification fragile (ARCH-10) and non-schema literals in the user layer (e.g. `false` instead of `true`) fail the *whole namespace* resolution rather than being pruned — the provider keeps last-good-value + warning on publish (verified in rc.1 d.ts), which is safe but means hand-edited YAML can silently freeze the last good config.
- **apply() not gating on connects**: right call for a fleet manager (one slow/broken server must not stall instance boot — the official row model *does* make activation wait on `ready`), but it creates the documented UX asymmetry: tools can legitimately appear after the first prompts, and with C3's no-status-visualization there is no UI signal between "connecting" and "broken" — logs only. Acceptable under C3/C4; recommend the design doc state this consequence explicitly.
- **Debt**: the force-path registration churn (ARCH-5), the unused `ready`/dead branch (ARCH-13), and the mirror-maintenance burden (Axis 6) are the main items.

### Axis 6 — Version/API surface risk
Compile target is the installed 0.1.2-rc.1 and every load-bearing API was verified against the rc.1 artifacts, not the rc.5 sources: `installSection` (+`SettingsSectionHooks` with live `setSource` thunk) exists only in rc.1's `SettingsProvider` (rc.5 has the free-function `installSettingsSection` — unused here, correctly); `ToolRuntime` layered scoped registration/restrict/view semantics, `createScope` + agent-as-scope-key, agent-loop `inject` (verified incl. the extra `sessionProjections`), `AgentRegistry.roots()/get(id)`, `agent/created|disposed` payload `{agent}` shapes, workspace registry `list()`/canonical-path membership, credentials `resolve`/`credentialRef`/`reference-updated`, cordis effect LIFO — all confirmed against anchor d.ts/js. Where the code *leans on rc.5 logic*, the divergence is explicit and documented (image bridge — the rc.1 artifact *does* ship one, ARCH-6; `resource_link` wording was taken from rc.1; reconnect policy identical in both). No rc.2-only behavior was found; the only rc.2 touches are *devDependencies* (`dsh-client-runtime@0.1.1-rc.2`), type-only and acknowledged (ui-notes §3). Runtime peer resolution relies on the two-anchor farm exactly as recon describes — this is where ARCH-1 bites: the farm is the fallback for *declared* peers; undeclared imports depend on it accidentally. Drift exposure on future dsh versions: peers allow any 0.1.x; the mirror discipline should include a re-diff against the installed `dsh-mcp-client` artifact (available in-closure) rather than only rc.5 sources, since rc.1 and rc.5 already differ in observable ways (image bridge, wire config vocabulary, apply-gating).
