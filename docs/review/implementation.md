## Summary verdict

The host half is a careful, largely line-faithful mirror of the official mcp-client supervisor and
tool bridge, adapted to a decoupled architecture (per-server master defs + per-agent-scope
registration gate). Every *architectural* deviation the code makes is deliberate and documented in
`docs/host-notes.md` §(c); I found **no accidental deviation in the reconnect math, the 5 s close
discipline, the two-phase swap, the naming contract, or the executor semantics** — those were
verified character-by-character against the official ref. State bookkeeping is defensive
(`isCurrent` double-checks, serialized chains, disposal quiescence) and the race analysis in §5
below found the supervisor/disposal and revoke/commit interleavings sound.

No critical findings. One **major** (workspace-scope staleness that contradicts the gate's own
invariant after a workspace deletion / directory disappearance), a set of minor behavioral
roughnesses (reconcile re-registration churn — proven by repro; credential-restart double-restart
race; give-up log/counter noise — proven by repro; orphaned override rows + dead `removeServerOverrides`),
and test-quality gaps (one test name overclaims what it verifies, several asserted-but-loose titles,
and whole branches of the executor/supervisor untested). See the findings table, coverage matrix and
prioritized actions.

### Per-agent gate (task §2) — verified answers

- **Workspace resolution** (`workspace.ts:23-30,39-50`): canonical equality via injected `realpathSync`; errors/deleted dirs → `undefined` → tools withheld at adoption (IMPL-1 for the staleness side); symlink spellings resolve (tested `model.spec.ts:165-190`); one `realpathSync` + one O(W) scan **per adoption**, i.e. per agent/created and per boot roots scan — acceptable, sync-IO on the main thread only at agent creation.
- **`enabled()` evaluation**: `isEnabled` default-on rule matches the model (`model.ts:55-58`), read live per push/reconcile (never cached — `agents.ts:123-124`), matching host-notes §c6.
- **Apply/revoke bookkeeping**: keyed per agent entry × server (`entry.applied: Map<serverName,{syncId,disposers}>`, `agents.ts:60-73`); disposers only ever invoked while `isAlive` (`agents.get(id) === agent`, `:121,146`); `agent/disposed` drops bookkeeping only (`:255-259`). Correct per the scope-ownership model, which is verified end-to-end by the harness (`agents.spec.ts:286-311` proves scope-ctx teardown removes entries).
- **Races**: `applyToEntry`/`pushServerState`/`reconcile` are fully synchronous — no interleaving with ctx teardown or event dispatch mid-loop is possible on the JS thread; register/dispose gaps cannot open between the `isAlive` check and the disposer loop (`:146-147`). The only cross-async hazards are the manager-level ones (IMPL-3) and adoption-order asymmetry (IMPL-6). “Events missed between activation and listener registration”: none — the effect setup (listeners then roots scan, `:250-260`) runs synchronously during `createManager`; double-adoption guarded by `entries.has` (`:130`).
- Note on production ordering: per the installed dsh-agent d.ts, `agent/disposed` fires *after* scoped-registration unwind — the harness (`agents.spec.ts:286-311`) instead keeps the scope alive across the event and asserts registrations survive until ctx teardown; behavior-equivalent for the plugin (bookkeeping drop only), but the test asserts a state production never reaches.

### Supervisor/manager (task §3) — verified answers

- **serverName identity diffing**: rename = remove + add (two passes in `reconcile`, `manager.ts:190-202`); vanish → `stopServer(revokeFirst=true)` (tools revoked before the handle is disposed); field change → dispose (defs stay committed/visible — deliberate crash-equivalent semantics, `manager.ts:148-150`) + start; new name → start. All handle mutations serialize on one chain (`:94-98`).
- **Restart-on-field-change granularity**: fingerprint = `JSON.stringify` of the schema-resolved def. Since schemastery resolves rows in schema key order (probed) and materializes defaults (`cwd:''` etc.), two reads of an unchanged doc stringify identically — **no cwd-`''`-normalization restart loop**; settings.spec (`:79-95`) and manager.spec step 2 confirm one restart per real change. Spurious restarts only for hand-edited YAML key reordering (resolved order is schema order — so not even that) — not a live issue.
- **Credential events**: filtered by refs-in-use from the live doc (`manager.ts:160-179`); restart enqueued on the mutation chain; races analyzed in IMPL-3 (convergent, redundant restart only). In-flight connect with the old value: the running attempt completes first (chain FIFO), then the restart picks the new value up at the next transport build — no lost update.
- **Failure containment**: no async rejection escapes — supervisor attempts never reject (`server.ts:295-365` catches all paths and the reconnect/give-up closures re-check `disposed`); manager enqueue tails are caught (`:97`); give-up closure is guarded; `applier` register/revoke/disposer throws are caught and logged (`agents.ts:147-154,196-205`). The one theoretical exception is a throwing `log.info`/`onDefsChanged` inside the give-up chain closure, which would poison `syncChain` until `dispose()`'s `await syncChain` re-throws into `stopServer` — swallowed upstream in `manager.dispose` (`:213`) but would break a later `restartServer`'s awaited stop; logger sinks are trusted, so severity nit-level.
- **Dispose ordering**: `manager.dispose` → `disposed=true` → drain mutations → stop every tracked handle with revoke-first → drain again; supervisors quiesce `settling` + `syncChain` after closing the live client (5 s capped close wait); applier's own effect teardown revokes while agents are alive. Both LIFO and FIFO effect unwinds of the four effects in `index.ts` were analyzed and are safe (revocations idempotent; post-dispose commits gated by `disposed` + `isCurrent`).
- **Single-instance guard**: `activeRoots` WeakSet keyed on `ctx.root` (`index.ts:43,54-60`), effect-scoped — mirrors the official reservation pattern; per-root, so multiple app roots in one process (tests) coexist.

### Settings wiring (task §4) — verified answers

- `installSection(ctx, 'mcp-scope', DocumentSchema, EMPTY_DOC, hooks)` with the live-thunk `setSource` correctly *stored* not called once (`index.ts:64,80-93` — matches the rc.1 contract, host-notes §a3). Attach fires `setSource` before `onChange`; the settings.spec mounts the real `FileSettingsProvider` and asserts attach counts (`settings.spec.ts:59-77`).
- Validate hook **aggregates** all `validateDoc` errors and throws once (`index.ts:87-92`; refusal leaves the stored section untouched — asserted `settings.spec.ts:97-110`). Schema-level validation (patterns, defaults, transports) runs before the hook (hook input is schema-valid by construction per the d.ts).
- Extra/unknown keys are **not dropped** (probed — see IMPL-9).
- No perpetual onChange loop: writes are deep-equal-gated by the provider; resolved doc normalization is stable (schema key order); onChange → `reconcile()` only re-judges; no write-back exists anywhere in the host half.
- **Secrets/redaction**: the document holds only credential *refs* (env-var names / header rows), never values — no `role('secret')` misuse, and no redaction need on the doc; values live in the credentials domain and are resolved per connect attempt (`manager.ts:101-102`, `transport.ts:47-86`).
- Path-op write surface: the client writes the whole `servers` array via one `set ['servers']` op (controller.ts:163) and per-cell `overrides` ops; the host only ever *reads* the resolved doc and never writes settings — the assumptions hold.
- `cwd:''` normalization: resolved rows always carry `args/cwd/envKeys`/`headers` materialized (probed + `settings.spec.ts:87-89`), and `transport.ts:109` maps `cwd ?? ''` — consistent.

### Error handling & observability (task §5)

- Stable `mcp-scope(serverName):` / `mcp-scope(agents):` prefixes used for every structured line (host-notes §c7); manager.spec asserts exact lines (`started/stopped/synced 8 tools/credential … reconnecting`), server.spec asserts the supervisor lines; agent apply/revoke lines are *not* asserted anywhere.
